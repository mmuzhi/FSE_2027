=== ANSWER ===
Looking at this problem:

**Key insight:** When "WA" is replaced by "AC", the 'W' disappears from the string (no new 'W' is ever created). Consider a maximal run of k consecutive 'W's immediately followed by an 'A': the leftmost-WA rule will consume this run from right to left (a cascade: `W^k A → W^{k-1}AC → ... → AC^k`), and this block fully resolves before any block further right is touched. Runs of 'W's followed by anything other than 'A' never participate in a "WA" pair (the character after them would need to be 'A'), and replacements never create new 'W's or new pairs across block boundaries.

**Plan:** Single left-to-right scan with a counter of pending consecutive 'W's:
- See 'W': increment counter.
- See 'A': emit 'A' + 'C' × counter, reset counter (the W-run gets absorbed).
- See any other char: flush pending 'W's literally, emit the char, reset.
- At end: flush remaining pending 'W's.

**Ledger check:**
- Invariant: counter = unresolved consecutive W's; they are consumed only if the very next character is 'A'.
- Edge cases: trailing W's (`WWWWW`), 'A' after flush (`WAA` → `ACAA`? — no: `WAA` → pending=1, first A emits `AC`, second A emits `A` → `ACA` ✓), separator chars (`WCA` stays `WCA`).

**Verification against samples:**
- `WACWA`: pending W, A→`AC`; C flush nothing →`ACC`; W pending, A→`ACAC`... result `ACCAC` ✓
- `WWA`: pending 2, A → `ACC` ✓
- `WWWWW`: flushed at end → `WWWWW` ✓
- Extra: `WWAW` → `ACC` + `W` = `ACCW`; direct simulation `WWAW → WACW → ACCW` ✓. `WWAA` → `ACC` + `A` = `ACCA`; simulation: `WWAA → WACA → ACCA` ✓.

Complexity: O(n) time and memory for n ≤ 3×10⁵.
